## Problem

The verdicts are stored per image and shown per image: in the column
(SPEC-002), the attachment details, and the filter of SPEC-007. A site
owner sees them only when they open the Media Library in list mode and
choose a filter. Nothing tells them, when they log in, how many images
verify, how many are marked AI-generated by their signer, how many do not
verify, or how many were never checked. Without that overview the plugin
is quiet about the one thing it found out.

WordPress has a place for this: a dashboard widget, added on
`wp_dashboard_setup` with `wp_add_dashboard_widget()`. The user can hide it
or move it with Screen Options; WordPress remembers that per user.

The counts come from what is already stored. SPEC-007 writes an index key
per checked image (`Index::STATE_KEY`, `Index::AI_KEY`) and filters on it;
SPEC-013 and SPEC-017 decide what "Check pending" and "Not checked" mean.
The summary counts the same rows the filter lists, so every number is a
link to a filtered list that shows exactly that many images. It adds no
verdict of its own.

Two limits on the wording, both deliberate:

- *No alarm.* Most photographs carry no Content Credentials; that is the
  normal case today, not a fault. "No Content Credentials" is shown as a
  count like any other, never as a warning or a task.
- *No promotion.* The widget informs and links only to the site's own
  screens. The WordPress.org guidelines forbid using the dashboard for
  advertising (guideline 11); this spec keeps it free of that entirely.

## Scope

**In scope**

- *One dashboard widget*, "Content Credentials", on the site dashboard
  (`wp_dashboard_setup`), for users with `upload_files`, the capability
  of the Media Library. On multisite: each site's own dashboard, with that
  site's images (SPEC-011); not the network dashboard.
- *One line per filter of SPEC-007*, in its order and with its exact
  label (`MediaSort::options()`): Verified: trusted signer; Intact: signer
  not trusted; Does not verify; AI-generated (signed); Could not be
  checked; No Content Credentials; Check pending; Not checked. Each line
  shows its count; a count above 0 is a link to
  `upload.php?mode=list&tracefern=<key>`. A line with 0 is shown without a
  link.
- *The count equals the filter.* For every key, the number shown is the
  number of images that list shows (same meta query, same pending cutoff,
  same MIME types for "Check pending" and "Not checked").
- *A total line* above them: "N JPEG, PNG and WebP images", the count
  `ExistingImages::count('all')` already makes. "AI-generated (signed)"
  overlaps the states (an AI image is also Verified or Intact); the widget
  says so in one sentence under the lines, so the lines are not read as
  adding up to the total.
- *For users with `manage_options`*, when "Not checked" is above 0: one
  link "Check them" to the Existing images section of Settings →
  Tracefern (SPEC-031). No button in the widget itself; the run starts
  where it always starts.
- *An empty site*: with no JPEG, PNG or WebP images the widget says "No
  JPEG, PNG or WebP images yet." and nothing else.
- *No storage.* No option, no transient, no user meta beyond what
  WordPress itself keeps for Screen Options; SPEC-005's uninstall needs no
  change.
- *`readme.txt`*: one line in the feature list. Within the 10,240-byte
  limit (SPEC-025, `tests/Unit/ReadmeTest.php`).

**Out of scope** (each needs its own spec before it may be built)

- Anything on the front end; anything shown to visitors.
- Admin notices, e-mail, or any message outside the widget.
- A count of "Result unreadable" (SPEC-007 has no filter for it, so the
  count would have no list to link to).
- Caching the counts (only if the measurement in the open questions says
  it is needed).
- Counts across the network on multisite.
- Charts, history over time, trends.

## Behavior

Acceptance criteria as Given/When/Then. Each is individually testable and will be
covered by a Pest test tagged `->group('SPEC-033')`, in `tests/Unit` when it
needs no WordPress and in `tests/Integration` (wp-env, WP-CLI) when it does.
At least one criterion MUST be an error / malformed-input path. This project
fails closed: it never shows a verdict the verifier did not give, a failure
is stored as state `error` with a reason, and the upload always proceeds.
Everything read from a file is untrusted text; a criterion that displays it
says how it is escaped.

- **AC1 — the counts equal the filters**
  - Given uploads of the OpenAI image (default settings), the Amazon Titan
    image (DigiCert off), `fixture-unsigned.jpg`, one image with an `error`
    entry, one with a fresh pending marker and one without any entry
  - When the widget is rendered
  - Then for every key of `MediaSort::options()` the shown count equals
    the number of attachments a `WP_Query` with that `tracefern` filter
    returns, the total is 6, and each count above 0 links to
    `upload.php?mode=list&tracefern=<key>`

- **AC2 — only for users who can upload**
  - Given a Subscriber and an Author
  - When each opens the dashboard
  - Then the Subscriber has no "Content Credentials" widget and the Author
    has it; the Author sees no "Check them" link, an Administrator does
    (when "Not checked" is above 0)

- **AC3 — an empty library**
  - Given a site with no JPEG, PNG or WebP attachments (a PDF only)
  - When the widget is rendered
  - Then it shows "No JPEG, PNG or WebP images yet." and no lines

- **AC4 — a failing count is not a zero** *(required: error path)*
  - Given a database error on one of the counting queries (a `query`
    filter that breaks it)
  - When the widget is rendered
  - Then that line shows "—" and the widget says the counts could not be
    read; no line shows 0 for a count that was not made, and the
    dashboard still loads

- **AC5 — multisite: each site its own**
  - Given two sites of a network, each with different images
  - When the dashboard of each is opened
  - Then each widget counts only its own site's images, and the network
    dashboard has no widget

- **AC6 — escaped and neutral**
  - Given any state of the library
  - When the widget is rendered
  - Then every label goes through `esc_html`, every link through
    `esc_url`, the output holds no link outside the site's admin, and no
    line is marked as a warning (no `notice-*` or error class)

- Oracle: the plugin's own filter (SPEC-007, `MediaSort::apply()`): the
  count for a key is the number of rows `upload.php?mode=list&tracefern=<key>`
  lists. The verdicts behind it are those of `provemark/c2pa-verifier`
  (the version in `composer.json`), already checked by SPEC-001 and
  SPEC-007. WordPress and PHP as in `.wp-env.json`.
- Reasoned: that a widget which reuses `MediaSort::apply()` cannot drift
  from the filter; that eight counts per dashboard view are cheap enough
  (to measure, see Open questions); that Screen Options covers hiding the
  widget, so the plugin needs no setting for it.

## API sketch

```php
// namespace Tracefern\ImageCheck;

final class DashboardSummary
{
    public function register(): void;          // add_action('wp_dashboard_setup', ...)

    /** @return array<string, int|null> key => count; null when the query failed */
    public static function counts(): array;    // per key of MediaSort::options(),
                                               // through MediaSort::apply() on a WP_Query
                                               // with 'fields' => 'ids', 'posts_per_page' => 1,
                                               // reading found_posts

    public function render(): void;            // escaped lines, links, "Check them"
}
```

## Open questions

- *Cost on a large library* (non-blocker for approval, blocker for
  `implemented`): measure the eight counts on 10,000 attachments in wp-env
  and write the time in `notes/`. If one dashboard view costs more than
  about 50 ms, a separate amendment proposes a short cache.
- *The widget's default position* (non-blocker): WordPress places a new
  widget in the first free column; the proposal is to leave that to
  WordPress.
